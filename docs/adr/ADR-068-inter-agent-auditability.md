# ADR-068: Inter-Agent Auditability — Three Correlation IDs, Multi-Agent Audit Trails

**ADR-ID:** ADR-068
**Status:** ACCEPTED
**Context:** 2026-09-02
**Owner:** Architecture Office

---

## 1. Context

Phase B directive B4 #30 ("AI Auditability") requires queryable, tamper-evident audit trails for AI agent actions. B4 #22 ("Multi-Agent Communication") requires that multi-agent workflows be auditable as a unit — the auditor must be able to reconstruct "which agent acting on behalf of which user, through which delegation chain, called tool T at time T'?" Stream 5 (`/home/z/my-project/phase-c-stream5-agent-runtime-report.md`) established the `AIAuditEvent` Prisma table (per ADR-046) with `correlationId` cross-referenced to `AuditEvent`, hash chain (tamper-evident), 7-year retention, and OpenTelemetry `gen_ai.*` spans (per ADR-059). Stream 5 also established the three-surface observability stack (Restate UI / OTel GenAI spans / `AIAuditEvent` table, per ADR-059).

Stream 6 identified Foundational Conflict **FC-6.6**: Stream 5's `AIAuditEvent` table captures single-agent audit fields (`agentId`, `toolId`, `model`, etc.) but does NOT capture the **multi-agent delegation chain** (`delegatingAgentId`, `delegationHop`, `parentInvocationId`, `originatingUserId`, `originatingUserRole`, `multiAgentTaskId`). Without these, multi-agent workflows cannot be reconstructed from the audit log. The amendment is additive (nullable for single-agent Phase 1 events) so historical audit events remain valid.

Stream 6 research (`/home/z/my-project/phase-c-stream6-multi-agent-report.md`, §10) confirmed the correlation-ID best practice across industry sources:

- AWS Well-Architected Agentic AI Lens (`https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec05-bp02.html`): "A correlation ID is generated by the application and propagated end-to-end, and it survives boundaries where trace context is re-generated (most commonly at service boundaries)."
- Comet AI: "Correlation IDs track requests across agent boundaries, enabling complete journey reconstruction even when agents run on different services."
- InsightFinder: "Trace ID and Span ID: Unique identifiers for correlation and debugging. Session ID: Links the trace to a broader multi-turn session."
- Armosec (`https://www.armosec.io/blog/minimum-viable-audit-trail`): "OpenTelemetry carries the schema and propagates trace context reliably; it does not carry kernel-level ground truth. For workloads where the ground truth matters, persist separately." — meaning OTel is for observability/evaluation, NOT for compliance.

W3C Trace Context (`https://www.w3.org/TR/trace-context`) defines the standard HTTP headers (`traceparent`: version-traceid-spanid-flags; `tracestate`: vendor-specific) for distributed tracing. W3C Trace Context Level 2 (`https://www.w3.org/TR/trace-context-2`, Mar 2024) is the current spec. OpenTelemetry GenAI semantic conventions (`https://github.com/open-telemetry/semantic-conventions-genai`) standardize `gen_ai.*` spans for LLM calls.

Restate's observability (per `https://docs.restate.dev/server/monitoring/tracing`): "Restate exports OpenTelemetry traces for all agent executions. Connect to your existing observability stack: LangFuse, Jaeger, or any OpenTelemetry-compatible backend. Each durable step appears as a span in the trace. **Cross-service calls (remote agents) are connected in a single distributed trace.**" Restate's "Nested calls" feature means every nested `ctx.serviceClient()` call inherits the parent invocation ID — the Restate invocation ID is the **primary correlation** for multi-agent workflows within Restate.

## 2. Problem

Should SmartAgentics use a single correlation ID (Restate invocation ID only), use OTel as the compliance surface, extend the existing `AuditEvent` table with multi-agent fields, adopt a blockchain audit ledger, use OpenInference instead of OTel GenAI, or adopt a three-layer auditability model with three distinct correlation IDs (Restate invocation ID / W3C `traceparent` / application `correlationId`)?

## 3. Options

### Option A: Single correlation ID (Restate invocation ID only)

Rejected. Doesn't survive delayed-message boundaries that start new invocations (the invocation ID changes); doesn't propagate to HTTP egress like Ollama calls. A multi-agent workflow that spans multiple Restate invocations (e.g., a delayed approval resuming hours later) cannot be reconstructed from the invocation ID alone.

### Option B: OTel as compliance surface

Rejected. Per Armosec: "OTel does not carry kernel-level ground truth." OTel is for observability/evaluation (Langfuse / Phoenix / Logfire per ADR-059); the `AIAuditEvent` Prisma table is the compliance surface (tamper-evident, 7-year retention). OTel is the _evaluation_ layer; the table is the _compliance_ layer.

### Option C: Extend the existing `AuditEvent` table with multi-agent fields

Rejected. Stream 5 already decided (per ADR-046): separate `AIAuditEvent` table, cross-referenced via `correlationId`, to keep human/system audit separate from AI audit. Extending `AuditEvent` would conflate the two audit surfaces.

### Option D: Blockchain audit ledger

Explicitly rejected. Phase B #42/#43 ("Blockchain — Explicitly Rejected — DO NOT ADD Phase 1"). The hash chain (per Stream 5 ADR-046) is sufficient for tamper-evidence.

### Option E: OpenInference (Arthur AI's alternative to OTel GenAI)

Rejected. OTel GenAI is the community standard; OpenInference is a vendor format. Reserved as a future exporter if a tool requires it.

### Option F: Three-layer auditability with three correlation IDs

Adopted. Layer 1 (source of truth): Restate journal — every routing decision, agent call, delegation hop, awakeable wait journaled; Restate invocation ID = primary correlation. Layer 2 (compliance): `AIAuditEvent` Prisma table extended with multi-agent delegation fields; hash chain; 7-year retention. Layer 3 (evaluation): OpenTelemetry GenAI `gen_ai.*` spans + W3C `traceparent`/`tracestate` headers for HTTP egress. Three correlation IDs (Restate invocation ID / W3C `traceparent` / application `correlationId`), each with a distinct purpose.

## 4. Decision

Adopt **Option F** — three-layer auditability with three correlation IDs.

### Three auditability surfaces (extends Stream 5 ADR-059)

1. **Restate journal** (source of truth): every routing decision, every agent call, every delegation hop, every awakeable wait is journaled. On crash, recovery replays the journal. The Restate invocation ID is the **correlation root** — every nested `ctx.serviceClient()` call inherits the parent invocation ID (Restate's "Nested calls" feature). This is the primary correlation for multi-agent workflows within Restate.

2. **`AIAuditEvent` Prisma table** (compliance surface): queryable projection of the journal, written by the Supervisor's finalize step. Stream 6 extends this table with multi-agent delegation fields (FC-6.6 resolution). Hash chain (tamper-evident per Stream 5) + 7-year retention (per Stream 5).

3. **OpenTelemetry GenAI spans** (evaluation surface): `gen_ai.*` semantic conventions for LLM calls (per ADR-059); W3C `traceparent`/`tracestate` headers propagated across any HTTP egress (Ollama, future cloud AI, future external A2A). The Restate invocation ID maps to the OTel trace ID.

### Three correlation IDs, each with a distinct purpose

| Correlation ID                  | Source                                                   | Purpose                                                                                                                                                          | Propagation                                                                                                                                     |
| ------------------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **Restate invocation ID**       | Restate runtime (auto-generated)                         | Primary correlation for multi-agent workflows within Restate. Durable, journaled, replayable.                                                                    | Auto-propagated across `ctx.serviceClient()` / `ctx.serviceSendClient()` calls (Restate "Nested calls" feature).                                |
| **W3C `traceparent`**           | W3C Trace Context spec                                   | Propagation across HTTP egress (Ollama calls, future cloud AI calls, future external A2A calls). Standard distributed-tracing format.                            | Propagated as HTTP headers (`traceparent` + `tracestate`) on every outbound HTTP call from a Restate handler.                                   |
| **Application `correlationId`** | SmartAgentics (UUID generated at top-level user request) | Survives Restate invocation boundaries (delayed messages, new invocations from `awakeable` resumes). The stable identifier across the full multi-agent workflow. | Persisted in `MultiAgentTask.correlationId` (per ADR-060); propagated in every `MultiAgentTask` payload; persisted in every `AIAuditEvent` row. |

The three correlation IDs are **complementary**, not redundant. The Restate invocation ID is the within-Restate primary; the W3C `traceparent` is the cross-HTTP-egress standard; the application `correlationId` is the cross-invocation-boundary stable identifier. The AWS Well-Architected guidance confirms: "A correlation ID is generated by the application and propagated end-to-end, and it survives boundaries where trace context is re-generated" — that is the application `correlationId`.

### `AIAuditEvent` extended fields (amends Stream 5 ADR-046 — FC-6.6 resolution)

```typescript
// Additive to Stream 5's AIAuditEvent — all nullable for single-agent Phase 1 events
export interface AIAuditEventMultiAgentFields {
  delegatingAgentId: string | null; // null for root agent
  delegationHop: number; // 0 for root
  parentInvocationId: string | null; // Restate invocation ID of parent
  originatingUserId: string; // the human who started the chain
  originatingUserRole: UserRole;
  multiAgentTaskId: string; // FK to MultiAgentTask — the correlation root
}
```

Phase 1 single-agent rows have `delegatingAgentId = null`, `delegationHop = 0`, `parentInvocationId = null` — backward-compatible with Stream 5's `AIAuditEvent` schema.

### `MultiAgentTask` Prisma table (new — correlation root)

One row per top-level task: `id`, `correlationId`, `tenantId`, `sessionId`, `state` (MultiAgentTaskState enum — A2A lifecycle per ADR-060), `parentTaskId`, `delegationHop`, `originatingUserId`, `originatingUserRole`, `agentId`, `requestedCapability`, `payload` (JSON), `deadline`, `createdAt`, `completedAt`. This is the correlation root for delegation chains.

### `AgentDelegation` Prisma table (new — one row per delegation hop)

Per ADR-061: `id`, `multiAgentTaskId` (FK), `parentAgentId`, `childAgentId`, `delegationDepth`, `scopeNarrowing` (JSON), `invocationId` (Restate), `correlationId`, `delegatedAt`, `resolvedAt`, `outcome`. Cross-referenced to `MultiAgentTask` and `AIAuditEvent`.

### Hash chain + 7-year retention

The hash chain (per Stream 5 ADR-046) is extended across `AIAuditEvent` rows within the same `correlationId` — tamper-evident. 7-year retention (per Stream 5, satisfying GDPR Art 15/16/17/20 per Stream 4 + financial audit requirements). Per-tenant partitioning for queryability.

## 5. Rationale

- **B4 #22 + B4 #30 satisfaction**: multi-agent workflows are auditable as a unit; the auditor can reconstruct "which agent acting on behalf of which user, through which delegation chain, called tool T at time T'?" without ambiguity.
- **FC-6.6 resolution**: `AIAuditEvent` is amended with multi-agent delegation fields (additive; nullable for single-agent Phase 1 events).
- **Three-layer auditability** extends Stream 5 ADR-059's three-surface observability stack with multi-agent delegation context. The three layers are complementary: Restate journal = source of truth; `AIAuditEvent` = compliance; OTel GenAI = evaluation.
- **Three correlation IDs** match the AWS Well-Architected guidance ("survives boundaries where trace context is re-generated") and the Comet AI guidance ("track requests across agent boundaries"). Each has a distinct purpose:
  - Restate invocation ID — within-Restate primary.
  - W3C `traceparent` — cross-HTTP-egress standard.
  - Application `correlationId` — cross-invocation-boundary stable identifier (survives `awakeable` resumes hours later).
- **OTel is for evaluation, NOT compliance** (per Armosec: "OTel does not carry kernel-level ground truth"). The `AIAuditEvent` Prisma table is the compliance surface; OTel is the evaluation surface (Langfuse/Phoenix/Logfire per ADR-059, deferred to Stream 8).
- **Blockchain explicitly rejected** (Phase B #42/#43). Hash chain is sufficient for tamper-evidence.
- **Restate's "Nested calls" feature** means the Restate invocation ID is auto-propagated across `ctx.serviceClient` calls — no SmartAgentics code needed for within-Restate correlation.
- **W3C Trace Context is the industry standard** for HTTP egress propagation. Adopting it now means future external A2A / cloud AI integrations are transparent to the audit trail.
- **Hash chain + 7-year retention** satisfies GDPR Art 15/16/17/20 (per Stream 4) and financial audit requirements.
- **Phase 1 ships the contract** (`MultiAgentTask` and `AgentDelegation` tables — always single-row for single-agent Phase 1; `AIAuditEvent` extended fields — null for Phase 1 root-agent events; three correlation IDs all in place).
- **No new runtime dependency**: Restate OTel export is in tree (per ADR-059); OpenTelemetry GenAI semantic conventions are attribute-naming conventions (no runtime dep); W3C Trace Context is standard HTTP headers (no runtime dep).

## 6. Consequences

- Stream 5's `AIAuditEvent` table (per ADR-046) is **amended** (separately, by the Phase D architect) to add nullable multi-agent fields — FC-6.6 resolution. Additive; backward-compatible.
- Stream 5's `AIObservabilityEmitter` (per ADR-059) is extended to emit multi-agent span attributes (delegation hop, parent invocation ID, etc.).
- New Prisma tables `MultiAgentTask` (correlation root) and `AgentDelegation` (one row per hop) — additive.
- The Supervisor's finalize step writes `AIAuditEvent` rows with the multi-agent fields populated from the `DelegationContext` (per ADR-063).
- **R-6.26 risk (three correlation IDs may confuse developers)**: mitigated by SDK helpers that centralize ID propagation; developers use `ctx.correlationId` not raw headers.
- **R-6.27 risk (`AIAuditEvent` table grows unbounded with multi-agent chains)**: mitigated by 7-year retention with archival; per-tenant partitioning.
- **R-6.28 risk (OTel GenAI spec still evolving)**: mitigated by pinning to a specific spec version; attributes are additive.
- **R-6.29 risk (hash chain breaks if a single event is inserted out-of-order)**: mitigated by Supervisor's finalize step writing events in deterministic order; chain validation on read.
- Dependencies: ADR-046 (`AIAuditEvent` table, amended); ADR-059 (Stream 5 `AIObservabilityEmitter`); ADR-060 (`MultiAgentTask` payload); ADR-063 (`DelegationContext` for audit field population); ADR-061 (`AgentDelegation` table); Restate OTel export (in tree); OpenTelemetry GenAI semantic conventions (attribute naming only); W3C Trace Context (standard HTTP headers). **No new runtime dependencies.**
- Future AI-BOS cross-tenant audit uses the application `correlationId` to survive tenant boundaries for chain-wide governance; AI-BOS agent marketplace accountability uses the delegation chain to attribute every delegated action to the originating human + the chain; AI-BOS compliance reporting uses 7-year retention + hash chain to satisfy GDPR + financial audit.

## 7. Review Conditions

- Review if Stream 8 (AI Security & Governance) adopts a different OTel evaluation backend (Langfuse / Phoenix / Logfire) that requires re-mapping `gen_ai.*` attributes — would extend the Layer 3 emitter.
- Review if the OpenTelemetry GenAI semantic conventions are revised in a way that requires re-mapping the `AIObservabilityEmitter` multi-agent span attributes (per ADR-059).
- Review if `AIAuditEvent` table growth exceeds the 7-year retention plan in production — would justify earlier archival or per-tenant partitioning tuning.
- Review if a community multi-agent audit standard emerges (e.g., a standardized multi-agent audit-event schema) that should replace the SmartAgentics-owned `AIAuditEventMultiAgentFields`.
- Review if Phase 3+ AI-BOS cross-tenant audit requires a separate `ChainAuditEvent` table distinct from `AIAuditEvent` (to preserve tenant isolation while still attributing chain-wide actions).
- Review if the hash chain proves brittle in production (e.g., out-of-order writes from concurrent multi-agent workflows) — would require strengthening the finalize-step ordering guarantee.
- Review if a PMS feature requires longer-than-7-year retention (e.g., a financial audit requirement for 10-year retention of refund approvals) — would require a separate `FinancialAuditEvent` table with its own retention policy.
- Review if the W3C Trace Context spec is revised (e.g., Level 3) in a way that requires re-mapping SmartAgentics' `traceparent` propagation.
- Review if a PMS feature requires auditing the _content_ of LLM inputs/outputs (not just metadata) for compliance — would require extending the existing PII-redaction pipeline (per ADR-059) to `AIAuditEvent.input`/`output` encryption.
